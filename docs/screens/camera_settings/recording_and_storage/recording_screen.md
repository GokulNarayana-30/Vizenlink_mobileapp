# RecordingScreen

- **Dart file:** `lib/screens/camera_settings/recording_screen.dart`
- **Route:** `/dashboard/live/:cameraId/settings/recording`
- **Purpose:** Configure the camera's local recording mode — Continuous, Scheduled, Event-Triggered, or Off — reached from a "Recording Mode & Schedule" row inside [storage_screen.md](storage_screen.md)'s Storage tab (not its own top-level camera-settings row any more — see that file's own doc for why). **Real, `RecordingModeClient`/`WanRecordingModeClient`-backed — added 2026-09-28**, closing what had been this screen's standing gap (`camera_api` had no recording-mode capability before this drop). Continuous/Scheduled/Event-Triggered load and save through `getMode()`/`setMode()` (LAN first, WAN retry on failure, per `.claude/rules/mobile-app-screen-conventions.md`), verified against a re-read on a timeout the same way every other real settings screen is. The mode selector is built from `CameraCapabilities.supportedRecordingModes` (`CapabilitiesClient.getCapabilities()`) — never a hardcoded four-way list — and "Add window" is capped at `CameraCapabilities.maxRecordingScheduleWindows`. **Off is real too, as of the same day** (a same-day follow-up after an initial pass left it silently local-only — a real gap found by review, not by a user report): `SETTINGS_API_GUIDE.md`'s own "Recording Mode" entry says Off is a different concept entirely — the separate Local Storage on/off toggle on [storage_screen.md](storage_screen.md) (`FR-CF-044`, `LocalStorageClient`/`WanLocalStorageClient`), not a fourth `RecordingMode` wire value. This screen presents both as one radio group, so Save and load keep them coherent rather than showing a state that isn't true: choosing Off disables Local Storage without touching whatever `RecordingMode` is configured underneath (so re-enabling storage later resumes that mode instead of forcing reconfiguration); choosing a real mode re-enables Local Storage first if it was off, then sets that mode. On load, Off is shown whenever Local Storage is confirmed disabled, regardless of what `RecordingMode` the camera reports underneath. A camera with no saved connection still falls back to fully local-only behavior for every mode. **Real, `RecordingsClient`-backed clip duration + delete-all — added 2026-09-07, moved out again the same day**: this screen briefly owned a Clip Duration slider (REC-014/015/016) and a Manage Recordings delete-all section (REC-017/018), both retired the same day once [storage_screen.md](storage_screen.md)'s Storage tab was rebuilt to be real and own both — duplicating them across two screens once both were real served no purpose. **Removed 2026-09-07**: the "Estimated footage retained" row (previously `REC-004`) — per direct user request/comparison against the sibling `nuraeye-rt` app's own recordings screen, storage capacity/retention estimates belong solely on [storage_screen.md](storage_screen.md), not mixed into this screen. REC-004/014/015/016/017/018 are all retired, not reused, per this repo's design-ID convention.

## Data model

- `Camera.recordingStatus` (`RecordingStatus`: `continuous`, `scheduled`, `eventTriggered`, `off`) — renamed from the previous `continuous`/`motionOnly`/`off` set; `motionOnly` became `eventTriggered` since it now covers all detection types, not just motion. Previously read-only (shown on [camera_info_screen.md](../camera_info_screen.md)'s CAMINFO-007 row) — this screen is the first place it's actually editable, since `Camera.copyWith` didn't even accept a `recordingStatus` override before this screen was added.
- `Camera.recordingScheduleWindows` (`List<RecordingScheduleWindow>`) — new field, only meaningful while `recordingStatus == RecordingStatus.scheduled`. `RecordingScheduleWindow` is `{ day (Mon–Sun), startMinutes, endMinutes }` (minutes since midnight; no overnight-spanning windows — model two windows instead).
- Maps to/from `camera_api`'s own `RecordingMode`/`RecordingScheduleWindow` (`recording_mode_types.dart`) via `_toWireMode`/`_fromWireMode`/`_dayToWire`/`_dayFromWire` in the screen itself — the wire day-of-week convention is `0`=Sunday..`6`=Saturday, distinct from this app's Monday-first `RecordingScheduleDay` enum, and `camera_api`'s `RecordingScheduleWindow` class name collides with this app's own model class of the same name (disambiguated with an `as wire` import in the screen file).
