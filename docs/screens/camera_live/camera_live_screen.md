# CameraLiveScreen

- **Dart file:** `lib/screens/camera_live/camera_live_screen.dart`
- **Route:** `/dashboard/live/:cameraId` (nested as a child route of the Dashboard branch inside the bottom-nav `StatefulShellRoute`, so the bottom nav bar stays visible here and throughout the whole Camera Settings sub-tree; see [navigation_flow.md](../navigation_flow.md))
- **Purpose:** Show a single camera's live feed with playback-style controls, and a secondary "Playback" tab for reviewing recorded footage. **Live tab video is real** for any camera with a saved LAN connection: `LiveViewController` (`lib/app_state/live_view_controller.dart`) implements `packages/camera_api/STREAMING_GUIDE.md`'s LAN WebRTC path end to end — `GetLiveStreamUri` discovery (`LiveStreamUriClient`, replacing the retired `GetWebRtcUri`/`WebRtcUriClient` 2026-09-11 — the camera now decides LAN transport itself, WebRTC or RTSP, per profile), offer/answer signaling over `package:flutter_webrtc`, no STUN/TURN (host candidates only, same-LAN), a grace window before an ICE `disconnected` blip is treated as a real drop, fresh-offer reconnect on a genuine drop, and a best-effort `POST /webrtc/stop` on teardown. **Real bug fix, 2026-09-11**: live view now always requests `kMobileOnlyStreamProfileToken` (`Profile_3`, the dedicated mobile stream) when no explicit profile is given — it used to default to `Profile_1` (the NVR/VMS-facing main stream), a real bug flagged in the updated `STREAMING_GUIDE.md`. **RTSP LAN fallback, real (2026-09-11)**: when the camera reports `LiveStreamTransport.rtsp` for this profile (its firmware build has `WEBRTC_STREAMING` disabled — the documented current default), `LiveViewController._connectRtsp` opens an `RtspLiveViewSession` (`lib/rtsp/rtsp_live_view_session.dart`, adapted from the Playback tab's `RtspReplaySession` — same DESCRIBE/SETUP/PLAY/digest-auth/H.264+AAC depacketization, but no seek/`Range:` concept) behind an `RtspLiveViewProxy` (`lib/rtsp/rtsp_live_view_proxy.dart`, adapted from `RtspRemuxProxy`) that remuxes to fMP4 over a local HTTP loopback for a plain `video_player` surface (`LiveViewController.lanRtspVideoController`) — still a same-network ("LAN") session, no "Remote" badge, same mute/health-monitor/reconnect treatment as the WebRTC path. This is a plain `video_player`, not a WebRTC `MediaStreamTrack`, so Talk and Record are unavailable on it (guarded in the UI with "isn't available on this connection", same message WAN already used) and Snapshot falls back to `_captureFrame`'s existing `RenderRepaintBoundary` screenshot path (the same fallback already used when there's no WebRTC track at all) rather than `MediaStreamTrack.captureFrame()`. The Live tab's default session also now pins `kMobileOnlyStreamProfileToken` permanently (`_profileLadderEnabled = false` unless an explicit `initialProfile` is passed, e.g. Multiview) so a healthy connection can never auto-step up to `Profile_1`/`Profile_2`, per `STREAMING_GUIDE.md`'s "never fall through, under any circumstance" rule. WAN fallback (KVS) is wired up here too — see below. The Live tab, for any camera with **no** saved connection, shows `_LiveUnavailable` ("Camera not connected") instead of any video — removed the previous bundled dummy sample clip fallback entirely 2026-09-07 per direct user request ("remove the dummy video in the app completely") rather than keep showing fake footage; in practice this state is rare since every onboarding path sets a connection and `isOnline` together, so `_OfflineThumbnail`/`_OfflineOverlay` (below) normally cover a disconnected camera first. **The Playback tab is real recordings, streamed live over RTSP, not the dummy asset and not a download-then-play temp file** (2026-09-07, `RecordingsClient` for the clip list + `OnvifReplayControlClient`/`lib/rtsp/` for the actual video — rebuilt entirely from the original `RecordingsClient.downloadClip`-based design) — see LIVE-003/LIVE-012/LIVE-036's rows below; a camera with no saved connection, or nothing recorded for the selected day, shows LIVE-051 ("No recording available") instead of any placeholder video. **The scrubber (LIVE-012) is `ScrollableRecordingTimeline`** (`lib/widgets/scrollable_recording_timeline.dart`, replacing the earlier non-scrolling `RecordingMapTimeline` 2026-09-07 per direct user request — "if 24 hour video is there how will user interact with that, the current bar is too small": a whole day's footage squeezed into one fixed-width bar gives too little precision per pixel to tap/drag accurately on a dense/continuous-recording day). This is a **new** widget (not a revert to the shared `CameraTimeline` [events_screen.md](../events/events_screen.md) still uses, and not `CameraTimeline` reused as-is either) — it borrows `CameraTimeline`'s already hardware-verified scroll/zoom shape (fixed center needle, the day's tape scrolls underneath, discrete zoom levels via LIVE-056/057) and its three already-fixed bug classes (re-entrant `animateTo`/`jumpTo` infinite recursion, tick-label edge-clipping, echoing a programmatic re-center scroll back as a fresh seek), but keeps `RecordingMapTimeline`'s own two-callback contract (`onSeek` preview-only, `onSeekCommit` firing exactly once per settled gesture) rather than `CameraTimeline`'s per-scroll-frame callback — `CameraTimeline`'s per-frame model is fine for Events' cosmetic browsing but would spam this camera's single-client RTSPS playback listener with a real session reopen on every scroll frame here. Snapshot (LIVE-009) and Record (LIVE-010) are real for the real live feed too: snapshot calls `MediaStreamTrack.captureFrame()` directly on the remote video track (not a screenshot of the video widget, which is unreliable for a texture-backed `RTCVideoView`) and record uses `package:flutter_webrtc`'s `MediaRecorder` against that same track — both still save via the `gal` package into the device photo gallery. Takes `homesController` and looks up the live `Camera` by id on every rebuild (via `ValueListenableBuilder`) instead of using a static navigation snapshot, so settings changed elsewhere (e.g. On-Screen Display's OSD toggles) are reflected immediately without leaving this screen. Also tracks the *phone's* own network type via `connectivity_plus` (LIVE-038/039/040) — a real, live-updating signal, independent of the camera's own Wi-Fi status shown elsewhere on this screen (LIVE-030). Privacy Mode and Video Mode also have quick-access shortcuts here (LIVE-041/042) so those two settings don't require a trip to Camera Settings — both call the real `camera_api` clients directly and apply immediately, unlike the full settings screens' draft-then-Apply convention. **Dev/test only**: this screen's `LiveViewController` reads the Dashboard's DASH-023 Force LAN/WAN override (`DebugTransportOverride`) at construction, and listens for it changing while already open — tearing down and reconnecting fresh under the newly-selected transport, so a tester doesn't need to physically leave the camera's LAN to exercise WAN live view.

## Playback tab works over WAN (2026-09-21)

The Playback tab was LAN-only: it listed clips with `RecordingsClient` and streamed them through
`OnvifReplayControlClient` + `RtspRemuxProxy`, so recorded playback simply did not work
off-network. It now runs on either transport. No element or design ID changed — the day picker,
timeline, and controls are the same; only the data and media source behind them differ.

- **Transport selection** — `isWan` is threaded down from `LiveViewController.transport`, never
  guessed from IP addresses (per `.claude/rules/mobile-app-screen-conventions.md` § LAN/WAN
  transport selection). It is `null` until live view actually connects, and the tab stays on the
  LAN path while unknown, reloading once the transport resolves or later flips.
- **Listing** — `_getRecordings()` picks `RecordingsClient` (LAN) or `WanRecordingsClient` (WAN).
- **Playback** — a `_ClipSession` abstraction has one implementation per transport:
  `_LanClipSession` wraps `RtspRemuxProxy`; `_WanClipSession` pairs
  `WanClipPlaybackClient.startClip()` (the camera pushes the clip into its `<thing>-playback` KVS
  stream) with a `KvsMediaLiveViewSession` reading it back. `_openClip`'s request-id guarding,
  assign-before-await and teardown ordering stay single-sourced across both.
- **One playback session camera-wide** — `_WanClipSession.stop()` stops the media session *and*
  sends `StopClipPlayback`, and a Start is always preceded by a Stop, so a session the app has
  forgotten about cannot block the next clip.

**Known difference:** WAN reports no server-side playback cursor, so
`_ClipSession.lastKnownPositionEpochSeconds` is null there and the timeline cursor follows the
player's own position. On LAN that value is only a fallback (used before the player reports a
position of its own), so visible behavior should match — this is the first thing to check on real
hardware.
